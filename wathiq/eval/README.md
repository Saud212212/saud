# التقييم (eval)

الغرض: قياس جودة الاستخراج على كراسات حقيقية بقوائم مرجعية تُعدّ يدوياً — وأهم مقياس
**نسبة التقاط المتطلبات الإلزامية** (recall)، لأن متطلباً إلزامياً فائتاً قد يستبعد العرض.

## الهيكل
```
eval/
├─ schema.ts              مخطط Zod للقوائم المرجعية وبيانات الكراسة
├─ validate.ts            npm run eval:validate — يتحقق من كل القوائم
├─ tenders/
│  ├─ _template/          انسخه لكل كراسة جديدة
│  │  ├─ meta.json        بيانات الكراسة وملفاتها (مع sha256)
│  │  ├─ gold.json        القائمة المرجعية (فارغة)
│  │  ├─ example-requirement.json   مثال لعنصر واحد
│  │  └─ source/          ضع ملفات PDF هنا (لا تُرفع لـ git افتراضياً)
│  └─ <slug>/             كراسة لكل مجلد
└─ runs/                  نتائج التشغيل (المرحلة 2)
```

## إعداد كراسة جديدة
1. `cp -r eval/tenders/_template eval/tenders/<slug>` (slug: حروف لاتينية صغيرة وأرقام وشرطات).
2. ضع ملفات PDF في `source/` وسجّلها في `meta.json`. البصمة: `sha256sum source/*.pdf`.
3. املأ `gold.json` بكل المتطلبات. لكل متطلب:
   - `quote` **حرفي** من الكراسة (سيُتحقق آلياً أنه موجود في الصفحة المذكورة).
   - `page` رقم الصفحة في ملف PDF (وليس الرقم المطبوع في التذييل إن اختلفا).
   - `obligation` و`disqualifying` بحسب نص الكراسة لا بحسب الاجتهاد.
4. `npm run eval:validate`.
5. يُفضّل أن يراجع شخص ثانٍ القائمة ثم `"reviewed": true`.

## إرشادات للمُعِد
- متطلب واحد لكل عنصر؛ إذا جمع بند واحد ثلاثة مستندات فهي ثلاثة عناصر.
- ما يتكرر في أكثر من موضع يُسجَّل مرة واحدة في أول موضع إلزامي، مع ذكر المواضع الأخرى في `notes`.
- نوّع الكراسات: نصية/ممسوحة/مختلطة، وجهات مختلفة، وأحجام مختلفة (50–300 صفحة).

## التشغيل
```bash
npm run eval:validate                  # تحقق من القوائم أولاً
npm run eval                           # كل الكراسات (عدا _template)
npm run eval -- --slug <slug>          # كراسة واحدة
npm run eval -- --slug <slug> --keep   # أبقِ المنافسة في المنصة لتصفحها بعد التقييم
```
- يحتاج قاعدة البيانات والإعدادات نفسها للعامل (`.env`)، و`ANTHROPIC_API_KEY`.
- **كل تشغيل يستدعي النموذج فعلاً.** كراسة من 300 صفحة ≈ 100–300 مقطع ≈ 100–300 استدعاء.
- للتكرار بلا كلفة (مثلاً عند تعديل التحقق أو الدمج دون البرومت):
  1. سجّل مرة: `AI_RECORD_DIR=/secure/rec npm run eval`
  2. أعد التشغيل: `AI_PROVIDER=replay AI_REPLAY_DIR=/secure/rec npm run eval`

  أي تغيير في البرومت أو النموذج يتطلب تسجيلاً جديداً.
- المنافسة تُنشأ في مؤسسة التقييم (`EVAL_ORG_ID`/`EVAL_USER_ID`؛ افتراضياً المالك التجريبي)، وتُحذف نهائياً بعد التقييم.
- **المثال `example-fixture/`:** كراسة اصطناعية بقائمة من 7 متطلبات. آخرها (المحتوى المحلي 40%) مصاغ خبرياً بلا «يجب/يلتزم» عمداً، لاختبار قدرة الاستخراج.

## المقاييس
| المقياس | التعريف |
|---|---|
| **التقاط الإلزامي** (mandatoryRecall) | المتطلبات الإلزامية المرجعية التي التقطها النظام **ومعروضة للمستخدم** (موثّقة أو تحتاج مراجعة) ÷ كل الإلزامية |
| التقاط المستبعِد (disqualifyingRecall) | نفسه للمتطلبات التي يُستبعد العرض بغيابها — الأهم عملياً |
| **المخترع مقارنة بالمرجع** (inventedRate) | متطلبات معروضة بلا أي مقابل في القائمة المرجعية ÷ كل المعروضة |
| غير الموثّق (fabricatedRate) | ما أعاده النموذج باقتباس غير موجود في الكراسة ÷ كل ما أعاده. هذا اختراع مؤكد، لكنه لا يصل للمصفوفة |
| الدقة (precision) | 1 − المخترع |
| اتفاق الصفات | الإلزامية، والاستبعاد، والفئة للأزواج المتطابقة |
| أخطاء في المرجع | اقتباسات في القائمة المرجعية لم توجد حرفياً في الصفحة المذكورة. راجع القائمة قبل الحكم على النظام |

**قاعدة المطابقة:** نفس الملف، وفرق الصفحة ≤ 1، ثم أحد شرطين: تداخل كلمات الاقتباس (بعد التوحيد العربي) ≥ 60% من الأقصر، أو تشابه نص المتطلب ≥ 50%. المطابقة متعددة إلى واحد، فمتطلب مستخرج واحد قد يغطي عنصرين مرجعيين.

**تنبيه في القراءة:** «المخترع مقارنة بالمرجع» يخلط بين اختراع حقيقي ونقص في القائمة المرجعية. كل عنصر منه مسرود في `runs/<وقت>/<slug>.json` (`unmatchedExtracted`) للمراجعة اليدوية. والعناصر الإلزامية الفائتة مسرودة في `summary.md`، مع التمييز بين «لم يره النموذج» و«رآه لكن اقتباسه لم يُتحقق منه».
